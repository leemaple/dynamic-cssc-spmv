## 2. v2 → v2.1 的四处修正

**① 问题 A 的指标此前是退化的（v2 的数学错误）**

v2 写"覆盖 80% overflow 所需的最少连续区间数"。不限制区间长度时，单个区间 `[0, r_b−1]` 覆盖全块，答案恒等于 1，指标无信息量。已替换为带覆盖跨度约束的 `Span₈₀(K)`，见第二部分。

**② 净合并不能跨新鲜度窗口**

v2 写"同坐标改十次算一个"，缺限定。若这十次之间存在必须看到中间状态的查询，合并会抹掉必须发布的版本，低估重加密、通信、compaction 和新鲜度违约。已改为**只允许在同一可见性窗口内合并**。

**③ F1 存在分量泄露（前五轮全漏，最重要的一条）**

分别返回 `Bx` 和 `Dx`，解密方拿到的是 2m 个线性约束，而不是 `y = Bx + Dx` 的 m 个，**严格泄露更多**。CSSC 原模型是两个互不串通的客户端，不能默认结果接收方有权看到基座与增量的分解。

**已采用的解法：服务器侧零和盲化**（见第 3 节）。这条同时补上了论文缺失的一个真贡献。

**④ 选了 F1，RM 连续切片就不再是第一优先级**

F1 允许客户端解密后任意重排，补丁层不必保持基座顺序，可按自己的行长排序——那就是 Mini-CSSC。RM 保序切片只在 F2 才有意义。方案优先级已重排，"我方/对手"的划分已取消（见第 4 节）。

## 3. 功能模型冻结：F1-M + 服务器侧零和盲化

**先明确泄露口径。执行前必须选定，不得由代理自行决定。**

| 口径 | 含义 | 适用 |
|---|---|---|
| **F1-L** | 允许解密方看到 `{Bx, D₁x, …, D_gx}` 各分量 | 仅当同一授权方同时拥有矩阵和向量，或应用明确允许分解泄露 |
| **F1-M** | 解密方只能得到总和 `y` | **本项目采用** |
| F2 | 服务器输出单一对齐密文，可继续参与 HE 计算 | 扩展实验 |

### 采用的盲化方案

服务器在明文域随机取零和掩码 `r₀ + r₁ + … + r_g = 0`（在逻辑输出域），分别加到各返回密文上。客户端解密、按各自 RowMap 重排、求和，掩码自动抵消。

**关键点：掩码必须由不解密的一方生成。** 若由解密方生成，它自己就能减掉，等于没盖。

**为什么由服务器生成：**

- 成本：`g+1` 次明文加法。**无上传、无新密钥、不需要任何一方额外在线**
- 依据：服务器与解密方不串通——这是 CSSC 模型里**本来就有的假设**，未引入新假设
- **退路一**：若威胁模型要纳入"服务器与解密方串通"，改由查询方生成掩码，代价是每次查询多传 `g+1` 个密文（此时补丁块数直接变成查询开销，必须计入模型）
- **退路二**：采用 F1-L，诚实写出泄露函数 `L_out = {Bx, D₁x, …, D_gx}`，并声明适用条件

### 这条带来的论文收益

"动态 CSSC 的分量泄露 + 零和盲化协议 + 由此产生的、随补丁密文数增长的代价"是 HE 特有的设计点，直接给出**补丁不能切太碎**的理论压力。这类内容正是之前论文骨架里缺的。

**盲化成本必须进成本模型**，不得当作零成本处理。

## 7. 已定案的技术事实（不许再犯）

1. **旋转偏移必须依据实测的 OpenFHE BFV packed layout 推导。** BFV 槽是 2-row 结构，旋转在行内进行，跨行需 row swap + mask + 组合。禁止按矩阵维度 n 取模，也禁止未经探针验证按总槽数 S 取模。
2. **只有 F2 要求补丁输出经 `RM⁻¹` 对齐**；F1 客户端明文合并不受此约束。
3. **密文不能像数组一样原地写槽。** 更新总是产生新的密文状态。可选机制包括 value-chunk replacement、加密修正量相加、以及基于 rotation/mask/shift 的服务器侧重排。**本项目第一版只用前两种**——这是范围选择，不是密码学普遍事实，论文里不要写成后者。
4. **不同水平行块的结果只能拼接，不能直接相加**，除非放进同一密文互不重叠的槽区。
5. **不写死噪声数字。** 只写"加法噪声远小于乘法噪声，系统通过微批合并、净修正与周期性密文替换避免无限累积"。
6. **不主张"首次支持密文更新"或"首次动态布局"。** Related work 必须主动写入 SELL-C-σ、HYB、LSM-tree、数据库 main/delta 架构——"切片""轻重行分离""基座+增量"都不是首创。

## Day 1：布局成本模拟器

Python 即可，**完全不涉及密码学，本质是数数**。

### 预处理（做错则全部结论作废）

**第一步：按可见性窗口切分事件流。** 遇到以下任一边界即提交当前净更新，**不得跨界合并**：

- 达到最大新鲜度 `F_max`
- 有查询要求看到最新版本
- 版本切换
- microbatch 结束

窗口内的净修正：

```
Δ⁽ᵉ⁾[i,j] = A[i,j] 在窗口末 − A[i,j] 在窗口初
```

**同一坐标在同一窗口内改十次算一个；跨窗口的更新必须分别提交。**
若窗口内反复更新后 `A[i,j] == B[i,j]`，该项完全消失，不计入任何 delta。

> 不加这条限制，任何策略都能靠无限拖延和跨时间合并伪造低更新成本。

**第二步：基于基座支持集分类**

```
M = {(i,j) | B[i,j] ≠ 0, A[i,j] ≠ B[i,j], A[i,j] ≠ 0}   修改
D = {(i,j) | B[i,j] ≠ 0, A[i,j] = 0}                    删除
I = {(i,j) | B[i,j] = 0, A[i,j] ≠ 0}                    插入
```

**第三步：按顺序处理**

1. `M` → value-chunk replacement 或加密净修正
2. `D` → 置零并留 tombstone
3. `I` → 依次尝试：tombstone → 既有 padding → 预留 slack
4. **剩余的 `I_overflow` 才进入补丁层，才计入 `k_i`**

判断一个 padding slot 是否**真正可用**，要看：所在 chunk、该行物理位置、列布局、能否在不改变 chunk 形状的前提下写入、对应 ColumnIndex 能否局部更新。**不得只统计 chunk 里的零槽总数**——那是虚假容量。

### 必须写死的定义（不得由代理临时发挥）

**Strict LocalRepack**："局部"指**受影响的固定水平行分区内的全部 CSSC chunks 重新生成，并发布该分区新版本**。必须冻结并写明：行分区大小、chunk 容量、是否允许重排、更新元数据范围。

> 结构性 Insert 会改变行度数进而改变 CSSC 排序，若允许重排则该分区的 RowMap 与 CI 都会变。定义模糊会让这个最强对手被不小心做弱。

**ReservedSlack(β)**：必须规定 slack 如何创建。二选一并写明：

- 每行显式占位符 `s_i = ⌈β · max(1, nnz_i)⌉`，再按有效长度 `nnz_i + s_i` 排序与 chunking
- 或 chunk fill factor 方式

两种成本结构不同，不能混用。

**强 Packed-COO**：必须批量装填多个修正 + 分段聚合。**禁止实现成"一条更新一个密文"**，那是稻草人。

### 每个策略的输出指标

- 每行 overflow 量 `k_i`（**复用之后**统计）
- 每片密文组数 `G_s = max_{p∈I_s} ⌈k_p / w_s⌉`，`w_s = ⌊S_eff / c_s⌋`
- 槽利用率 `η = Σk_i / (G·c·w)`
- value 密文数
- **查询侧密文数**（含补丁带来的额外 X_Δ）
- 更新重传密文数
- compaction 密文数
- 所需 rotation index 集合（**按 P0a 实测表推导**）+ 旋转密钥数量
- 元数据同步量
- **盲化开销**：掩码数量、明文加法次数；若采用退路一（查询方生成），另计上传密文数
- **客户端合并类另需**：返回密文数、下载字节数、解密次数、客户端重排与合并时间

### 问题 A 的诊断（次要，F2 相关）

对 `K ∈ {1, 2, 4, 8}` 计算：

```
Span₈₀(K) = min over 至多 K 个连续区间的选择 { 圈进的行数 / r_b }
            约束：被圈进的行贡献 ≥ 80% 的总 overflow
```

即：**最多允许 K 个连续区间时，为覆盖 80% overflow，至少要圈进全块多少比例的行。**

若使用 2 的幂切片，区间须额外满足：长度为 `2^q`、起点对齐、不得任意切边界。

读法示例：`K=4` 时只需圈进 12% 的行 → 热点集中，连续切片有希望；`K=4` 必须圈进 85% → 热点散乱，RM 连续切片无意义。

可顺带报告滑动窗口 Spearman 相关作为描述性数据。**诊断指标不得直接判死任何策略，生死一律由成本模拟决定。**

### 负载要求

**合成流必须包含**：Zipf 偏斜、热点迁移、单行热点、多行热点、突发更新、增删混合、同坐标重复修改。

**真实流的事件语义必须预先定义。** 时间网络数据通常只给 `(u, v, t)`，不告诉你这是首次插入、权重修改、重复交互还是过期删除。至少实现两种语义之一并写明：

- **T1 累计权重矩阵**：首次出现 = Insert，再次出现 = Modify（权重加一），无 Delete。测 value-chunk replacement，但结构 overflow 较少。
- **T2 滑动窗口邻接矩阵**：窗口 W 内的边为非零。进入窗口 = Insert，重复事件 = Modify，离开窗口 = Delete。产生完整的 I/D/M 流，**优先采用**。

或直接使用 LDBC SNB 的正式 insert/delete update streams。

**均匀分布只用于正确性自检，不作为通过依据。**

### 因果调参（防事后调参）

所有策略都有可调参数（PeriodicRepack 周期、β、compaction 阈值、切片数与高度、合并位置、microbatch 大小）。用完整测试流事后选最优参数 = 使用未来信息。

真实流必须拆成三段：

1. **warm-up**
2. **tuning prefix** —— 在此选参数
3. **held-out evaluation suffix** —— 参数冻结，只依据历史窗口做在线调整

知道未来的最优结果**只能标注为 `Offline Oracle`**，不得作为正常实现结果参与判定。

```
QA_bytes = B_query_dynamic / B_query_static
新鲜度 F = t_visible − t_arrival
```

## 48 小时判定（三级，不得混淆）

判定必须在 **held-out evaluation suffix** 上进行。

### 第一级：动态维护研究线继续

至少一种策略（含参考策略）在 held-out 真实偏斜流上形成**非孤立 Pareto 优势区间**。

"非孤立" = 不是单点获胜、不是只在均匀数据获胜、在一段连续 ρ 区间内有效、计入输出放置 + 旋转密钥 + 查询侧密文 + 盲化开销后仍有效。

### 第二级：算法型论文成立

**候选贡献**（hybrid selector / 新 overflow 机制 / 合并位置选择 / 盲化协议）相对**全部固定参考策略**形成稳定优势。

### 第三级：仅基准型备选

若只有 PaddingReuse、Mini-CSSC 或其他已有策略胜出：

> **不能自动认为论文贡献足够。** 进入"动态维护策略表征"备选路线，重新做新颖性核验与目标期刊核验，**并改题**。

优势强度参考（任一即可）：更新通信或加密量降低约 2×；综合成本降低 15%–20%；相同新鲜度下明显减少重传密文；存在宽度合理的 break-even 区间。

### 无条件停止条件

1. 只有均匀更新有效
2. 只有忽略输出搬移成本才能获胜
3. 只有忽略旋转密钥成本才有收益
4. 只有忽略盲化开销才有收益
5. 更新通信下降但查询侧密文暴增，综合无任何合理区间
6. 只在人工设置的单一极端点获胜
7. 优势只在 tuning prefix 上存在，held-out suffix 上消失
